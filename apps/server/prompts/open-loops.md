# Open loops morning check

Use the existing schedule. Do the work yourself. Read the local `memory/open-loops.md` and its maintenance rules first, using the path in your memory instructions. If memory is off or the ledger is unavailable, report that limitation; do not invent a ledger or enable memory. Never load the historical migration backup routinely.

Keep the existing morning candidate sources. If the memory folder has a `memory/proposals/` directory beside the ledger, read every `*.md` in it, excluding `_archive/`. Also inspect the available pending draft cards and their original threads using existing tools. A candidate need not already be in the ledger. Check the ledger for matching outcomes, holds, fit vetoes and notice history before surfacing it. Do not add a chat-search feature or treat a missing ledger entry as proof that a draft is unsent or a proposal unapplied.

Reconcile before choosing a reminder. Read each candidate's original completion source, not just its summary or daily log. A recorded delivered message closes its matching send action; an unsent draft does not. A completed ticket closes only the action it proves. Respect later failure/reversal evidence and explicit rejection. Use exact source identifiers, not broad chat searches. Source failure or incomplete results leave status uncertain, never open or done by assumption. Excluding a reminder does not close the work: a proposed extension leaves the action unresolved until its outcome is known, and a tentative idea without an existing task requires neither creating nor closing anything. Check the most relevant candidates within the run's budget; defer unverified items without presenting them as obligations.

Update the matching line immediately with the current action, owner, evidence reference and actual checked date. Keep completed and cancelled action identities in the ledger's suppressed section, so the memory maintenance pass cannot recreate them from an old daily. Declining a planning suggestion suppresses that suggestion only: keep the underlying action unresolved unless the user also cancels the work. Preserve prior notice markers when shortening, merging or rewording a line. Before editing, reread that line and preserve concurrent changes. Do not edit any other file in the memory folder. No mail, Slack, ticket or calendar writes; no new routines, events or work items inferred from advice.

Choose at most one useful suggestion in the original priority order, after reconciliation. First, a last-centimeter action the user can close now, such as an unsent draft, unanswered reply or outstanding check. Require a still-relevant agreed action and verify its original completion source, even if it was absent from the ledger; then add or update its current-state line. Second, if the memory folder keeps proposals, a ready proposal in `memory/proposals/` for a profile file: read its own preconditions and the current target passage to confirm it is still applicable and unapplied. When several proposals edit the same passage, use only the newest superseding proposal as one combined suggestion. Offer it as an optional decision, not an obligation; never edit the profile file or turn the proposal into an active task without the user's commitment. A suppressed uncommitted-context entry prevents treating a proposal as owed work, not considering it for this optional choice; explicit rejection and previous notice history still suppress another suggestion.

For either of these first two choices, only publish when a concrete useful action exists and waiting has a real cost. Record `Reminder: <current timestamp>; <source revision>` before publishing, on the matching action or suppressed proposal-context line. Preserve the proposal's non-task status, source identity and prior markers. Reread before writing; a failed write or changed marker means do not publish. An absent item does not establish empty notice history: check available original history first. Do not repeat without material new evidence, and keep unknown history suppressed. Offline completion may warrant one uncertainty question when it matters, recorded before publishing, never repeated assertions that work is unfinished.

Only if neither earlier choice qualifies, check at most one confirmed deadline within the next seven calendar days, including today, for an active, source-verified action owned by the user. Read every connected calendar for the period from now to that deadline, including all result pages, and identify an actual work block for this action. A similarly named unrelated meeting is not a work block. If any calendar cannot be read completely, do not claim a block is missing. An unconfirmed deadline, completed item, explicit rejection, an existing work block, or a non-empty/unknown prior deadline-notice marker excludes the suggestion.

For an eligible item, reread the line and record `Deadline notice: <current timestamp>; proposed` before publishing. If the write fails or the marker changed, do not publish. Keep that marker after a stopped or failed run; accepting a missed suggestion is preferable to repeating it. State the concrete action, confirmed deadline and source in at most two sentences in the user's language. Propose planning, never book it. If the user declines, mark it declined in the same line; do not reset it when the date changes. Only an explicit new request can reopen a rejected proposal.

Write all published prose in the user's language, including draft nudges, optional proposal suggestions, uncertainty questions and failed-check reports, not just deadline suggestions. Use at most two short sentences naming the action and why it matters today. If nothing qualifies, follow the enclosing routine's quiet/output protocol and never fabricate a suggestion to fill the run. For a project run, close with `0 urgent items` or `1 proposal`, in the user's language; for a DM, retain its machine quiet/publish markers. A failed source check is reported as a failed check, not as a missed task or an empty calendar.
